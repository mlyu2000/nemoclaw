# NemoClaw (OpenClaw) — PCAI port

This folder ports **NVIDIA NemoClaw / OpenClaw** (an always-on AI-agent gateway)
to HPE Private Cloud AI (PCAI) as a BYOA Helm import, following the
[frameworks repo structure](https://github.com/ai-solution-eng/frameworks).

## Layout (per the frameworks guideline)

| Path | Purpose |
|------|---------|
| `logo.svg` | Logo shown in the PCAI portal (NVIDIA symbol). |
| `nemoclaw/0.1.0/` | Version folder — the Helm chart for NemoClaw 0.1.0 (OpenClaw 2026.3.11). |
| `nemoclaw/nemoclaw-0.1.0.tgz` | Helm package of `0.1.0/` (top-level dir = `nemoclaw`, the containing folder name). |
| `porting.md` | This file — how the framework was ported to PCAI. |

## What the chart does

A single-gateway sandbox app exposed on the PCAI Istio `ezaf-gateway` as
`https://nemoclaw.<your-pcai-domain>` (an Istio `VirtualService`), with:

- **Static dashboard URL + static gateway token** — both baked at import time
  (no post-deploy curl/scrape). The token is generated by the PCAI portal or
  entered in the values form.
- **OpenClaw gateway** bound to LAN on port 18789, `dangerouslyDisableDeviceAuth`
  enabled (all-device pairing) and `allowedOrigins: ["*"]`.
- **LLM via the PCAI internal LiteLLM proxy** (`litellm-helm` in
  `<litellm-namespace>`), model `qwen3-8-27b-int4-dflash2-r2` (the registered
  name — note the `-r2` variant).
- **Auto-connecting dashboard from the bare URL** — the PCAI portal "Open"
  button opens `status.endpoints.external` = the bare root URL (a VS host can't
  carry a `#token=` fragment). The chart serves the control-ui from a writable
  root (`gateway.controlUi.root`) on the PVC and injects a same-origin
  `auto-token.js` (the gateway CSP `script-src 'self'` blocks inline scripts)
  that sets the Control UI token and connects. So the bare URL lands on an
  already-authenticated, working dashboard.
- **Persistent state** — `/sandbox/.openclaw` (sessions, workspace) on the
  PVC (`<pcai-storageclass>`, default `nfs-csi`).
- **Telegram channel (optional)** — `telegram.enabled` + `telegram.botToken`
  register the channel in `openclaw.json`. On each pod start a **one-off
  validation** (`files/telegram-verify.js`) runs *before* the gateway starts:
  `getMe` proves the token + outbound egress to `api.telegram.org`, then a
  single test message is sent to a chat (the most recent from `getUpdates`, or
  `telegram.testChatId`). It is bounded (20s) and non-fatal (`|| true`), so it
  can never block the deploy; results land in
  `/sandbox/.openclaw/telegram-verify.log`.
- **Access control** — `telegram.allowAll` (default `true`) sets
  `dmPolicy`/`groupPolicy=open` + `allowFrom=["*"]` so **anyone** can use the
  bot (no per-device pairing approval). Note: with `dmPolicy=open` the OpenClaw
  config validator *requires* `allowFrom` to include `"*"` — the chart adds it
  automatically. Set `allowAll=false` to fall back to OpenClaw's default
  "pairing" gate (each new user must send a pairing code, approved via
  `openclaw pairing approve --channel telegram <CODE>`).

## PCAI-specific adaptations

- **Domain / gateway**: exposed on the `ezaf-gateway` Istio gateway. The base
  domain is a deploy-time variable (`domain.base`), so the dashboard host
  `nemoclaw.<domain.base>` is fully dynamic and not tied to any single PCAI
  platform.
- **EzAppConfig / EZUA**: registered via an `EzAppConfig` CR
  (`ezconfig.hpe.ezaf.com`) so the PCAI portal shows the app + "Open" button and
  health. `spec.values` carries the full baked `values.yaml`;
  `ezua.virtualService.endpoint` drives `status.endpoints.external`.
- **LiteLLM auth**: the master key is fetched live from the cluster secret
  `litellm-helm-masterkey` (`<litellm-namespace>`) at deploy time and injected
  into the chart — it is **never committed** (the committed `values.yaml` uses a
  placeholder).
- **Istio sidecar**: the gateway pod gets a sidecar (namespace
  `istio-injection: enabled`); the sidecar forwards `X-Forwarded-For`, which the
  auto-connect script handles transparently.
- **Memory**: the OpenClaw gateway's V8 heap is capped by the container memory
  limit (~521MB at 1Gi). Enabling a chat channel (Telegram long-poll + in-memory
  update queue) pushes it past that → `JavaScript heap out of memory` at
  startup. `resources.limits.memory` is therefore **2Gi** (gives Node a ~1.4GB
  heap). Without a channel the gateway runs comfortably at 1Gi.

## Deploy (via the PCAI portal — no kubectl)

1. **PCAI portal → Applications → Import / Deploy** (the BYOA flow).
2. **Point it at this framework** — upload the `nemoclaw-0.1.0.tgz` chart (the
   portal also picks up `logo.svg` and `porting.md`). It creates the
   `EzAppConfig` and installs the chart.
3. **Fill in the values** in the portal's values form: `domain.base` (your
   PCAI base domain), `litellm.apiKey` (the LiteLLM master key — fetched from
   the `litellm-helm-masterkey` secret or pasted), `litellm.baseUrl` /
   `litellm.model`, `persistence.storageClassName`, and optional `telegram.*`.
   Secrets are entered in the UI and are **never committed**.
4. **Deploy.** The portal shows install progress and, once done, a **ready / ok**
   health state plus the dashboard URL and "Open" button.

The import is idempotent — re-running it re-applies the values and re-deploys.

## Verification (via the PCAI portal — no kubectl)

1. **App health** — PCAI portal → **Applications → `nemoclaw`** → status
   **ready / ok**. Open the app's **Logs** tab for the gateway logs.
2. **Dashboard** — click **"Open"** (or `https://nemoclaw.<domain.base>`). It
   should show **Health OK** and a working **Chat** section (send a message,
   get an LLM reply).
3. **Telegram channel** (if enabled) — the bot sends a **one-off test message**
   on first deploy; after that it replies to DMs / group messages. A pairing
   code means `telegram.allowAll` is `false` — set it to `true` and re-deploy.

> No `kubectl` is needed — the portal gives app status, the "Open" button, and
> a Logs view.
